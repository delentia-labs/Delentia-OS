# นโยบายเวอร์ชัน (ภาษาไทย)

*ฉบับอังกฤษ (ฉบับหลัก): [VERSIONING_POLICY.md](VERSIONING_POLICY.md) · ข้อเท็จจริงที่ตรวจพบ: [VERSION_AUDIT_2026-10-26.md](VERSION_AUDIT_2026-10-26.md) · ประวัติการเผยแพร่: [RELEASE_HISTORY.md](RELEASE_HISTORY.md)*

## คำตอบสั้น ๆ: ตัว `.exe` ควรเป็นเวอร์ชันอะไร? ใช่ v0.1 หรือไม่?

**ไม่ใช่ v0.1 ครับ** ตัวติดตั้ง `.exe` ใช้ **เลขเวอร์ชันเดียวกับ runtime ที่มันติดตั้ง** คือ `2.4.0` ชื่อไฟล์ `Delentia-Setup-2.4.0.exe` (และสำเนาชื่อคงที่ `Delentia-Setup.exe` สำหรับลิงก์ดาวน์โหลดที่ไม่เปลี่ยน) ส่วน "**Public Technical Preview 0.1**" คือ **ชื่อของหมุดหมาย (milestone)** ไม่ใช่เลขเวอร์ชัน ใช้ในหัวข้อ Release Notes, README และหน้าเว็บ ไม่ใช้เป็นชื่อไฟล์ ไม่ใช้เป็นเลข Windows file version และไม่ใช้เป็น git tag

เหตุผลที่เป็นข้อเท็จจริงจากการตรวจ ไม่ใช่ความเห็น:

1. **ตัวติดตั้งไม่ใช่ผลิตภัณฑ์แยก** มันบรรจุ wheel ของ runtime ไว้ข้างใน ติดตั้งแล้ว `delentia --version` จะตอบ 2.4.0 ถ้าไฟล์ติดตั้งเขียนว่า 0.1 แต่ในเครื่องเป็น 2.4.0 ผู้ใช้จะสับสนว่าอะไรคือเวอร์ชันที่ตนใช้ และเมนู "เพิ่ม/ลบโปรแกรม" ของ Windows จะแสดงเลขที่ขัดกับโปรแกรมจริง
2. **การแจ้งเตือนอัปเดตเทียบเลขกับ PyPI** (`delentia update`) เลข 0.1 จะถูกมองว่าต่ำกว่า 2.3.1 ที่อยู่บน PyPI แล้ว
3. **PyPI ไม่รับเลขที่ต่ำกว่าหรือซ้ำ** และ workflow ปล่อยรุ่นของโครงการใช้ `skip-existing: true` คือถ้าส่งเลขที่ถูกใช้แล้วจะ "สำเร็จแต่ไม่ได้เผยแพร่อะไรเลย" โดยไม่แจ้ง
4. **ที่สำคัญที่สุดที่ตรวจพบ: 2.3.1 เผยแพร่ไปแล้ว (2026-10-16) และไม่มีของใหม่เลย** (ไม่มีหน้าเว็บ Desk, launcher, passkey, plan-first, ตัวติดตั้ง) มีอีก 270 commit ที่อยู่หลังมัน ดังนั้นรุ่นถัดไปต้องเป็นเลขที่สูงกว่า 2.3.1 และตามกติกา SemVer การเพิ่มคำสั่ง/หน้า/เครื่องมือโดยไม่ลบอะไรคือ **minor = 2.4.0**

## สามคำถามที่ต้องไม่ปนกัน

| คำถาม | ตอบด้วย | ตัวอย่าง |
|---|---|---|
| นี่คือ build ไหน และใหม่กว่าที่ฉันมีไหม | **เวอร์ชัน** ของแต่ละส่วน (SemVer, เพิ่มขึ้นอย่างเดียว) | `2.4.0` |
| เปิดอะไรให้ใครแล้ว | **milestone** (ป้ายชื่อ ผูกกับระดับการเผยแพร่ L0–L4) | *Public Technical Preview 0.1* |
| ไบต์ที่ทดสอบจริงคืออะไร | **บันทึกที่มา** (git commit, ค่าแฮชของไฟล์, รหัสโมเดล, ผลการทดสอบ) | commit `a1b2c3d`, SHA-256 ของตัวติดตั้ง |

## แต่ละส่วนมีเลขอะไร เก็บที่ไหน

| ส่วน | เลขเก็บที่ (พิมพ์ที่เดียว) | เผยแพร่ที่ | tag |
|---|---|---|---|
| runtime Python `delentia-os` (รวมหน้าเว็บ Desk ที่อยู่ใน wheel) | `pyproject.toml` | PyPI + GitHub Release | `vX.Y.Z` |
| ตัวติดตั้ง Windows | ไม่มีเลขของตัวเอง: ใช้เลขของ wheel ข้างใน (เลข Windows 4 ส่วน = `X.Y.Z.<revision ของตัวติดตั้ง>` โดย revision เป็น 0 เว้นแต่แก้สคริปต์ติดตั้งโดยไม่แก้ runtime) | GitHub Release | tag ของ runtime |
| Desk (หน้าเว็บ) | ไม่มีเลขของตัวเอง (อยู่ใน wheel) | พร้อม runtime | |
| TypeScript SDK `@delentia/delentia-os` | `sdk-typescript/package.json` | npm | `sdk-vX.Y.Z` |
| MCP connector `delentia-mcp` | repository ของมันเอง | npm + MCP registry | ของมันเอง |
| Tauri desktop shell | ไม่เคยเผยแพร่ เลขไม่ใช่เลขรุ่น | ไม่แจกจ่าย | |

เลข **พิมพ์ที่เดียว** ที่อื่นต้องอ่านจากที่นั่นหรือถูกตรวจเทียบ: `scripts/check_versions.py` ล้ม build เมื่อเลขที่ต้องตรงกันไม่ตรง README ไม่มีเลขที่พิมพ์เอง ป้ายใน README อ่านจาก PyPI

## ความหมายของเลข (SemVer ปรับใช้กับโครงการนี้)

- แก้บั๊ก/แก้เอกสาร/เพิ่มความเข้มงวดความปลอดภัยที่ไม่เปลี่ยนสิ่งที่คำสั่งที่เขียนไว้ทำ → **PATCH** (2.4.1)
- เพิ่มคำสั่ง ตัวเลือก route เครื่องมือ หน้า หรือรูปแบบไฟล์ โดยไม่ลบอะไร → **MINOR** (2.5.0)
- ลบหรือเปลี่ยนชื่อสิ่งที่เป็น "พื้นผิวสาธารณะ" (คำสั่ง `delentia`, API `/v1/`, รูปแบบไฟล์ของผู้ใช้, ชื่อ/อาร์กิวเมนต์ของเครื่องมือ) → **MAJOR** (3.0.0)
- เลขแพ็กเกจ **ไม่ได้บอกความพร้อม** ความพร้อมคือ release level และ gate ใน `RELEASE_LEVELS.md`

## กติกาที่ไม่ยืดหยุ่น

1. เลขเพิ่มขึ้นอย่างเดียว ห้ามเลขต่ำกว่าที่เผยแพร่แล้ว ห้ามใช้เลขซ้ำ
2. รุ่นที่เผยแพร่แล้วไม่ถูกแก้ ความผิดพลาดแก้ในรุ่นถัดไปและบันทึกเป็น "การแก้ไขข้อมูล (correction)" ใน `RELEASE_HISTORY.md` (เช่น PyPI ของ 2.3.1 ยังเขียนว่า Production/Stable แก้ย้อนหลังไม่ได้)
3. หัวข้อ changelog ของเวอร์ชันหนึ่งอธิบายเฉพาะสิ่งที่อยู่ใน tag ของเวอร์ชันนั้น (ร่างแรกเคยใส่ฟีเจอร์ของ 2.4.0 ไว้ใต้ 2.3.1 ตอนนี้ตัวตรวจจับได้)
4. **milestone ไม่เคยเป็น git tag** เพราะ `v0.1.0` จะถูก workflow อ่านเป็นเลขแพ็กเกจ

## milestone: ป้ายบอกว่าเปิดอะไรให้ใคร

โครงการมี **ระดับการเผยแพร่ L0–L4** และ **gate** อยู่แล้ว ([RELEASE_LEVELS.md](RELEASE_LEVELS.md)) milestone คือจุดหนึ่งบนบันได

> **Delentia OS — Public Technical Preview 0.1** = ระดับ **L1**: ใครก็ติดตั้ง runtime (pip หรือตัวติดตั้ง Windows) แล้วรันบนเครื่องตัวเองกับโมเดลที่ตนเลือก โดยมีคนดูแล และตรวจได้ว่ามันทำอะไร **เปิด**: `pip install delentia-os`, ดาวน์โหลดตัวติดตั้ง, เดโมแบบสคริปต์, Desk บนเครื่องของคุณเอง **ยังปิด**: โฮสต์ที่ใช้ร่วมหรือสาธารณะ, ให้คนอื่นใช้ช่องแชท, และคำกล่าวใด ๆ ว่ามีโมเดลที่เก่งพอขับเอเจนต์แล้ว (นั่นคือ L2)

- ป้ายนี้ **ไม่ใช่เวอร์ชันและไม่รีเซ็ตเวอร์ชันใด**
- **เจ้าของเป็นผู้ประกาศ ไม่ใช่การ build**: `status` ใน `docs/release/compatibility.json` เป็น `planned` จนกว่าเจ้าของจะเปลี่ยนเป็น `declared` พร้อมใส่ commit และค่าแฮชของสิ่งที่ทดสอบ ปล่อยรุ่นก่อนประกาศ milestone ได้ (เป็นรุ่นธรรมดา)
- gate ที่ยังไม่ผ่านเขียนว่าไม่ผ่าน ไม่ปัดขึ้น ตอนนี้ที่ยังไม่ผ่าน: ตัวติดตั้งทดสอบบนเครื่องสะอาด/SmartScreen/โหมดออฟไลน์, Windows Hello จริง (และ G-model เป็นของ L2 ไม่ใช่ milestone นี้)
- ป้ายถัดไปเป็นแผนเท่านั้น: 0.2 External Validation Preview, 0.3 Research Evidence Preview, 1.0 Validated Research Baseline ตาม gate ไม่ใช่ตามวันที่ และไม่เปลี่ยนเลขแพ็กเกจใด ๆ

## ตัวติดตั้ง Windows

- ชื่อไฟล์ `Delentia-Setup-<เวอร์ชัน runtime>.exe` + สำเนาชื่อคงที่ `Delentia-Setup.exe` + `SHA256SUMS.txt`
- ลิงก์ใน README: `https://github.com/delentia-labs/Delentia-OS/releases/latest/download/Delentia-Setup.exe` (ใช้ได้เมื่อมี release ที่แนบตัวติดตั้ง คือ 2.4.0 เป็นต้นไป)
- ไม่ใส่ชื่อ milestone ในตัวไฟล์ และ **ยังไม่ลงนามรหัสโปรแกรม** SmartScreen จะเตือน (README บอกไว้ข้างลิงก์)
- ติดตั้งแล้วแพ็กเกจที่ runtime พึ่งพามาจาก PyPI ตอนติดตั้ง (ไม่ใช่สำเนาสภาพแวดล้อมทั้งหมดที่ตรึงไว้)

## ขั้นตอนปล่อยรุ่น (เจ้าของเป็นผู้ push tag)

1. เลือกเลขตามหัวข้อความหมายของเลข ตั้งใน `pyproject.toml` และ `rct_control_plane/_version.py`
2. ใส่บันทึกใต้ `## [X.Y.Z] - วันที่` ใน `CHANGELOG.md` (ไม่ใช่ `Unreleased`)
3. `python scripts/check_versions.py --registry` เลขตรงกันและยังว่างบน PyPI
4. ปรับ gate ใน `compatibility.json` และ `RELEASE_LEVELS.md` ให้ตรงความจริงวันนี้
5. CI เขียวบน commit นั้น (เทสต์ 3 เวอร์ชัน Python, ตรวจเวอร์ชัน, ตัวติดตั้ง Windows)
6. `git tag vX.Y.Z && git push origin vX.Y.Z` workflow จะตรวจ tag กับแพ็กเกจ สร้าง wheel (มี Desk) เผยแพร่ PyPI สร้าง GitHub Release และสร้าง ติดตั้ง ตรวจ แล้วแนบตัวติดตั้ง
7. ตรวจจากภายนอก: `pip install delentia-os==X.Y.Z` ใน venv ว่าง, `delentia --version`, เดโม; ดาวน์โหลดตัวติดตั้งจากหน้า release แล้วเทียบกับ `SHA256SUMS.txt`
8. ถ้างานล้ม **หลัง** อัปโหลด PyPI ให้รันซ้ำเฉพาะงานที่ล้ม (หรือสั่ง *Windows installer* ด้วยมือพร้อม tag) การรันทั้ง workflow ซ้ำจะล้มที่ขั้น "เลขยังว่าง" ตั้งใจให้เป็นเช่นนั้น

## สิ่งที่ตั้งใจไม่ทำ

- ไม่ลดเลขรุ่นที่เผยแพร่แล้วให้ดูเหมือนเริ่มใหม่ (`2.x` อยู่ต่อ; "0.1" คือ milestone)
- ไม่มี tag `v0.1.0` ไม่มีแพ็กเกจ `0.1.0` ไม่มีชื่อแพ็กเกจที่สอง
- ไม่ใช้เลขเวอร์ชันแทนคำกล่าวเรื่องความพร้อม
