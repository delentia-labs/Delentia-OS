# ระบบคิดอย่างไร: ดูจากงานจริงหนึ่งงาน (ร่างให้ตรวจ ยังไม่เผยแพร่)

หน้านี้ไม่ต้องอ่านโค้ด มันพาดูว่า Delentia ทำอะไรกับคำสั่งหนึ่งข้อ ทีละขั้น โดยใช้ผลที่ **รันจริงเมื่อ 7 พ.ย. 2026** ไม่ใช่ภาพจำลอง
ลองเองได้ใน 5 นาที โดยไม่ต้องมีโมเดล AI และไม่เสียเงิน:

```bash
delentia demo init --lang en
delentia demo run compare --scripted
delentia demo status
```

**ข้อความสำคัญที่ต้องอ่านก่อน:** เดโมนี้ใช้ "สคริปต์" แทนโมเดล AI คือลำดับขั้นและถ้อยคำของคำตอบถูกเขียนไว้ล่วงหน้า สิ่งที่ **จริง** คือเครื่องมือ ไฟล์ ประตูความปลอดภัย การรอลายเซ็น และบันทึกตรวจย้อน
หน้านี้จึงสอนว่า "ระบบที่ล้อมโมเดลอยู่ทำอะไร" ไม่ได้บอกว่าโมเดลตัวไหนฉลาดแค่ไหน (เรื่องนั้น ณ วันนี้ยังไม่เคยวัดกับโมเดลออนไลน์ที่เก่ง)

## งานที่ใช้เป็นตัวอย่าง

> อ่านใบเสนอราคาในไฟล์ `quotes/vendor_a.md`, `vendor_b.md`, `vendor_c.md` ทำตารางเทียบราคา แล้วบอกว่าเจ้าไหนอยู่ในงบ 15,000 USD อย่าแก้ไฟล์ต้นฉบับ และอย่าส่งข้อมูลออกไปที่ไหน

คำสั่งนี้มีสามอย่างปนกัน: งานที่ต้องทำ (อ่าน เทียบ ตอบ) ข้อจำกัด (งบ 15,000) และข้อห้าม (ห้ามแก้ ห้ามส่งออก)

## ภาพรวม: ทุกงานผ่านแปดขั้นนี้

```
ตรวจที่ประตู → คิดเป็นแผน → เลือกทางเร็ว/ช้า → ลงมือ (ทีละก้าว ผ่านประตูทุกก้าว)
      → ย่อข้อมูลยาว → ตรวจคำตอบกับสิ่งที่ขอ → จดบันทึกที่แก้ไม่ได้ → เรียนรู้เฉพาะที่ตรวจแล้ว
```

ด้านล่างคือแต่ละขั้น กับสิ่งที่เกิดขึ้นจริงในงานนี้

### 1. ตรวจที่ประตู (GUARD)
ก่อนทำอะไร ระบบอ่านคำสั่งว่ามีสิ่งที่เหมือนการพยายามหลอกให้ทำเรื่องอันตรายหรือไม่ (เช่น "ลืมคำสั่งก่อนหน้า") ในงานนี้ไม่พบอะไร จึงไปต่อ
**ทำไมสำคัญ:** ถ้าคำสั่งหรือข้อความที่อ่านมาซ่อนคำสั่งแปลกปลอม มันถูกหยุดตั้งแต่ตรงนี้

### 2. คิดเป็นแผน (THINK, RCT-7)
ระบบแยกคำสั่งเป็นเจ็ดขั้นตามแนวคิด RCT-7 ผลจริงของงานนี้:

| ขั้น | ผลที่ระบบได้ |
|---|---|
| 1 สังเกต | จับประโยคคำสั่งทั้งหมด |
| 2 วิเคราะห์ | ประเภทงาน = ค้นหา/อ่าน (QUERY) ขอบเขต = ไฟล์ |
| 3 แยกส่วน | พบ 1 ข้อจำกัด: `COSTLTE0.0` |
| 4 คิดย้อน | ระดับความเสี่ยง = SYSTEMIC |
| 5 หาเจตนาแกน | ตรวจผ่าน ไม่มีคำเตือน |
| 6 สร้างใหม่ | แปลงสำเร็จ ลำดับความสำคัญ = ปานกลาง |
| 7 ยืนยัน | รหัสยืนยัน `CRYSTAL-HASH-a2d9e8cec8db102e` |

**ต้องบอกตามจริง:** สองแถวนี้ **อ่านผิดหรือหยาบ** และเป็นข้อมูลที่ควรรู้
- แถว 3: "งบ 15,000 USD" ถูกแปลงเป็นข้อจำกัด `COSTLTE0.0` (ค่าใช้จ่าย ≤ 0.0) ซึ่งไม่ตรงกับสิ่งที่ผู้ใช้เขียน
- แถว 4: งานนี้อ่านอย่างเดียวแต่ถูกจัดเป็นความเสี่ยงระดับสูงสุด (น่าจะเพราะมีคำว่า "ส่งข้อมูลออก" ในข้อห้าม)

ตัวแยกส่วนนี้ทำงานด้วยกฎ ไม่ใช่ด้วยโมเดล มันเร็วและอธิบายได้ แต่หยาบ ผลคือไม่มีขั้นใดตัดสินผิดเรื่องความปลอดภัยในงานนี้ (ผิดไปทางระวังเกิน ไม่ใช่หลวม) แต่นี่คือหลักฐานว่า **"RCT-7 ในโค้ดวันนี้" ยังไม่ใช่การคิดเชิงลึก** และยังไม่มีผลวัดว่ามันทำให้คำตอบดีขึ้น

### 3. เลือกทางเร็วหรือทางช้า (ROUTE)
งานอ่านง่าย ๆ ได้ทางเร็ว (จำกัดจำนวนก้าว) งานซับซ้อนได้ทางช้า

### 4. ลงมือทีละก้าว ผ่านประตูทุกก้าว (ACT)
ระบบทำสามก้าว: อ่านไฟล์ A, อ่านไฟล์ B, อ่านไฟล์ C แล้วตอบ ทุกก้าวถูกตัดสินโดยประตู FDIA:

> `delentia_read_repo_file`: D=0.6 I=1.5 A=1.0 → F=0.4648 (เกณฑ์ 0.5) → **ผ่าน** (เป็นการอ่านที่นโยบายของคุณอนุญาต จึงไม่ใช้เกณฑ์ D/I กับการอ่าน)

วิธีอ่าน: D คือข้อมูลที่มีรองรับ, I คือความชัดเจนและความเข้มงวดของเจตนา, A คือการที่มนุษย์เจ้าของระบบอนุญาต ถ้า A = 0 ผลลัพธ์เป็น 0 เสมอ (ไม่มีเจ้าของรับผิดชอบ ไม่มีสิ่งที่จะเกิดขึ้น) สำหรับการอ่าน ระบบอนุญาตได้เลย
แต่ถ้าคำสั่งคือ "แก้ไฟล์" ระบบจะหยุดและรอลายเซ็นของคุณ (ลองดูด้วย `delentia demo run edit --scripted`)

### 5. ข้อความจากข้างนอก = ต้องระวัง (TAINT)
ไฟล์ใบเสนอราคาอยู่ในโฟลเดอร์ที่ประกาศว่า "ไม่น่าเชื่อถือ" ระบบจึงจดว่า:

> งานนี้อ่านข้อความจากข้างนอก → ตั้งแต่นี้ **ทุกอย่างที่ส่งข้อมูลออกหรือเปลี่ยนแปลงอะไรต้องให้คนเซ็นก่อน**

กฎนี้ไม่ขึ้นกับว่าโมเดลฉลาดหรือโดนหลอกหรือไม่ ถ้าในใบเสนอราคามีประโยคแฝงสั่งให้แก้ไฟล์ โมเดลอาจเชื่อ แต่ระบบไม่ยอมให้ทำโดยไม่มีลายเซ็น (ดูด้วย `delentia demo run injection --scripted`)

### 6. ย่อข้อมูลยาว (COMPRESS)
ถ้าเครื่องมือส่งข้อความยาวมาก (เกิน 6,000 ตัวอักษร) ระบบจะย่อให้โมเดลอ่านเฉพาะที่เกี่ยวกับคำสั่ง และเก็บต้นฉบับไว้เรียกคืนได้ ในงานนี้ไฟล์สั้น จึงไม่ย่อ

### 7. ตรวจคำตอบกับสิ่งที่ขอ (VERIFY)
คำตอบที่ได้: ตารางราคา เรียงจากถูกไปแพง พร้อมสรุปว่า Harbor HVAC (9,900 USD) ถูกสุดและอยู่ในงบ
เดโมตรวจคำตอบนี้ด้วย **ตัวตรวจของมันเอง ไม่ใช่ตัวตรวจของโมเดล**:
- ✔ ตารางมีราคาครบทั้ง 3 ใบ
- ✔ บอกว่า Harbor HVAC และ Northwind Cooling อยู่ในงบ
- ✔ ไม่บอกว่า Polar Systems (เกินงบ) อยู่ในงบ
- ✔ ไฟล์ต้นฉบับไม่ถูกแก้

**ต้องบอกตามจริงอีกข้อ:** ตัวอ่านเงื่อนไขของ runtime เอง (ไม่ใช่ของเดโม) **ไม่ได้** แปลงประโยค "อย่าแก้ไฟล์ต้นฉบับ" เป็นเงื่อนไขที่ตรวจได้ในงานนี้ (ผลคือรายการเงื่อนไขว่าง) เงื่อนไขที่เห็นข้างบนมาจากตัวตรวจของเดโม
จึงยังมีช่องว่างระหว่าง "ผู้ใช้เขียนข้อห้ามไว้" กับ "ระบบตรวจข้อห้ามนั้นให้เองทุกครั้ง"

### 8. จดบันทึกที่แก้ไม่ได้ (RECORD)
ทุกก้าวถูกจดลงบันทึกที่ผูกกันเป็นโซ่ด้วยลายเซ็น: **11 แถว เซ็นแล้ว 11 แถว สภาพโซ่: ไม่ขาด** ถ้ามีใครแก้แถวเก่า โซ่จะขาดและตรวจพบ
(แต่ถ้าผู้โจมตีมีกุญแจและเขียนโซ่ใหม่ทั้งเส้น ต้องมีพยานภายนอกจึงจะจับได้ ซึ่งตั้งค่าแยกต่างหาก)

### 9. เรียนรู้ (LEARN)
ระบบเรียนรู้เป็น "ทักษะ" เฉพาะจากงานที่ตรวจผ่านและไม่เคยอ่านข้อความจากข้างนอก งานนี้อ่านข้อความจากข้างนอก จึง **ไม่ถูกเรียนรู้** นี่คือการตั้งใจให้เรียนช้าแต่ไม่เรียนสิ่งที่อาจถูกยัดมา

|---|---|---|
| มันทำอะไรไปบ้าง | รายการก้าว ชื่อเครื่องมือ และข้อมูลที่ส่ง | ส่วน "What the agent did" ในผลลัพธ์ |

| คำตอบตรงกับที่ขอไหม | ตัวตรวจแยกจากตัวทำ | ส่วน "answer checked" |
