## Amendment 4 (2026-11-15, written after windows 1 to 3 and before any further command of round two; approved by the Architect the same day)
Found by window 3 (register R0097, commit `a0de0d02`). In two of the 14 d0 runs of haiku (seeds 1704 and 1709, both k = 6) the episode ended `llm_error`: the last three requests were identical and every reply stopped at the 2,048-token allowance with an empty message. The loop's own recovery for an unusable reply (one more request with a 4,096 allowance, `decide_next_action`) never ran, because `llm_provider.reply_text` raises `LLMReplyError` for an empty message before the loop sees any text, and `_is_transient_llm_error` then re-sends the identical request (up to 2 more times) with the same allowance. A reasoning model that spends its allowance thinking therefore cannot get the second, larger allowance. (The mechanism is read from the code and the call log; that haiku spent the tokens on hidden reasoning is probable, not shown.)

**What is changed (and only this).** An empty message whose choice reports `finish_reason == "length"` raises a new `LLMReplyCut` (a subclass of `LLMReplyError`, `transient = False`, so the identical request is not re-sent). `decide_next_action` treats it as an unusable first reply and makes the one retry it already has, with the 4,096 allowance; if that retry is also cut, the episode ends `parse_error` as for any second unusable reply. An empty message with any other finish reason stays transient and is retried exactly as before. No prompt, tool, rule, price, seed or oracle changes.

**Pass rule for the fix, written before the code.** (1) New tests that fail on the old code and pass on the new: `reply_text` raises `LLMReplyCut` for an empty message with `finish_reason` `length` and `LLMReplyError` (transient) for one with `stop`; a provider that is cut at 2,048 and answers at 4,096 gives a decision with exactly two requests, the second with `max_tokens` 4096; a provider cut at both gives `parse_error` after exactly two requests; an episode through the governed loop with the first kind of provider finishes without `llm_error`. (2) The related suites (provider failure modes, loop, budget, rehearsal of the paid path) pass. (3) CI is green on the merge commit.

**Which windows are re-run.** Windows 1 and 2 (R2-1, judge and critic) stay at `a0de0d02`: all 12 of their runs report 0 unusable replies and 0 provider errors, so no reply of them was cut and the change cannot alter them. Windows 3 to 8 run at the commit after the fix, with new freezes W and R written at that commit; the round is therefore at two commits, stated in every entry. R0097 stays registered as the record that found the defect; it is not replaced and its verdict stays `inconclusive`. The new window 3 is the primary TC-003 result for haiku.

**Stops, written now before the re-run (they were not written before window 3).** A pair of TC-003 is dropped from the paired count, and listed, if either run ended `llm_error`, `parse_error`, `budget_exceeded`, by a token, money or time limit, by a crash, or was not valid. A run that ended `stuck_repeating` or finished by itself stays in the pair: the runtime's own stop is part of what is measured. If fewer than 10 pairs remain the model is `inconclusive`. The rule for "helping", "no effect shown" and "harmful" is the one in section 3.
