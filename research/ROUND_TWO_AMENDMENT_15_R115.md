# Round two, Amendment 15 (2026-11-18, written before the change to the runtime and before any further paid run): the repeated-call rule must not stop an edit-and-test loop

## What the data showed (read, free)
TC-003 visible tier, haiku, arm d0 (the Delentia governed loop), seeds 5000 to 5041, 42 runs, commit e4ee857b, key `delentia-r2l-t2` (Keys page $0.262, driver 42 x $0.006245): oracle passed 3 of 42 (7%), hard failures 1, mean score 69.1. **30 of the 42 episodes ended `stuck_repeating`**, 9 `llm_finished`, 3 `parse_error`. The same tasks with arm b0 (headroom screen, 14 runs): passed 9 of 14, all `llm_finished`.
The tool sequence of the d0 episodes (read from `events.jsonl`, seeds 5000, 5003, 5004): run the public tests, search, read two to five files, write ONE file, run the public tests, run the public tests, and stop. `delentia_run_public_tests` takes no arguments (`{}`), so every call has the same fingerprint. `GovernedAutonomousLoop._judge_tool_call` counts calls by the hash of (tool, arguments) over the whole episode and stops at the third (`envelope.limits()["repeat_limit"]`, default 3). The first call was made before any edit; the second and third after an edit. The results of those calls differ (the workspace changed), but the rule does not look at the result.
Earlier data with the same cause, smaller: round-two R2-2 (mixed k = 2 to 6): d0 ended `stuck_repeating` in 3 of 14 (R0097) and 2 of 14 (R0098), b0 never.
Running the tests again after a change is how an agent that edits code checks its work; stopping it for doing so is a defect of the runtime, and it made the d0 arm lose by a mechanism that says nothing about whether the runtime helps.

## Change (the rule only; the limit, the audit row and every other stop are unchanged)
A call counts as repeated only while the RESULT of the repeat is the same as the result of the previous call with the same fingerprint. When a call with the same fingerprint returns a different result, the count of that fingerprint restarts at 1 (the call that changed the result is the first of a new run). The result compared is the hash of what the tool returned, before screening and compression (the hash already taken for the audit). With identical results the behaviour is exactly as before: the third request of an unchanged call is not run, the audit row `stuck_repeating` is written with `times`.
Known limit, stated in the change: a tool whose result changes by itself every time (a time stamp, a counter) is no longer stopped by this rule; the episode is still bounded by `max_iterations`, `max_seconds`, the cost cap and the daily limits.

## Rules, written before the change
F1 Free tests (the first two already exist and must pass unchanged): (a) the same call with the same result three times stops at the third request, the third is never run; (b) different calls are not stuck; (c) the same call whose result changes every time is NOT stopped for as many calls as the iteration limit allows; (d) results A, B, B, B: the count restarts at the change, so the stop comes at the fourth request (the third request of the run of B); (e) the same call, an effect call between them that changes the result, then the same call again twice: not stopped; (f) `stuck_repeating` audit row unchanged in shape; (g) the repeat limit variable still works.
