# Efficacy study, stage S0.7 (2026-11-18): criteria written before any code

Context: `DELENTIA_EFFICACY_STUDY_PLAN_R114_DRAFT_FOR_REVIEW.md` (claims C1 to C6, hypotheses H1 to H9, stages S0 to S7) was approved by the Architect on 2026-11-18, with the order "controllable, recoverable, cheaper, then succeeds more" and an initial budget of about $15 to $50 for S1 and S2. This file fixes what S0.7 builds and how it is judged. S0.7 costs no money.

## Why the stage exists (what the week of 2026-11-13 to 11-18 showed)
1. A comparison between the Delentia loop and a plain agent is only worth reading when the two arms differ in the thing being tested. In TC-003 the d0 arm had, besides the Delentia loop, a structure the b0 arm did not have: every write waits for a signature and the episode continues afterwards with a note. That structure alone made d0 stop after one write in 39 of 42 episodes (Amendment 17), and the repeated-call rule stopped edit-and-test loops (Amendments 15 and 18). A fair comparison needs an arm that has the approval structure and not the Delentia loop: `+sig`.
2. A comparison needs tasks both arms sometimes pass. The mixed TC-003 tasks gave 0 of 14 for both arms; the visible tier (7 tasks) gave 9 of 14 for b0. Seven tasks are a screen, not a study: the confirmatory stage needs hundreds of distinct units, so the generators of the research domains need a difficulty setting that can be calibrated and versioned.

## Part A: the `+sig` arms
A1 `b0s`, for the TC-003 benchmark (`python -m research.daaes benchmark --arms b0s`): the plain agent of `research/plain_agent.py` with the SAME write approval structure as d0: a write to `ledgercalc/` is executed only after the benchmark's rule-bound signer has approved it, exactly as in `run_session(approve=True, approve_if=...)`, and the model is then told what d0's model is told after an approval (the same note, built by the same function `GovernedAutonomousLoop` uses, not a copy), so that the only differences between `b0s` and `d0` are the Delentia loop's own parts (gate, FDIA, RCT-7 plan and prompt, memory, repeated-call rule, audit). No other change to the plain agent.
A2 For the research harness (`research/runner.py`, quotes and tickets): `GP` and `PL` already exist. The harness does not exercise signed approvals (the runner's own header says so), so the confound of A1 is absent there; this is checked, not assumed: a manipulation check counts, per arm, the episodes that end `pending_approval` (a write that waited and never continued); the primary comparison A111 against GP is only read when that count is zero in every arm. If it is not zero, `GP+sig` is built before the comparison, by the same rule as A1.
A3 Tests, free: (a) `b0s` on the scripted rehearsal gives the same final workspace as `b0` when the signer approves everything; (b) a write outside `ledgercalc/` is refused in `b0s` as in `d0`; (c) the note a `b0s` model reads after an approval is byte-for-byte the one a `d0` model reads (same function, same arguments); (d) the arm names appear in the result rows and the analysis table; (e) nothing of `b0s` runs without the same key, freeze and budget guard as the other arms.

## Part B: difficulty settings for task generation
B1 TC-003 variants: the three tiers are named and pinned by tests: `V` (visible, seeds from 5000, 7 tasks, defects shown by the visible tests), `M` (mixed, seeds below 5000, k = 2 to 6, as before) and a new `H` tier (hidden-heavy, seeds from 6000: at least two defects the visible tests do not show, k = 3 to 5). `V` and `M` do not change.
B2 Research domains (`research/generate_tasks.py`, `generate_tickets.py`): a `--level` option (1, 2, 3) that changes only the size and the traps of a task (the number of quotes or tickets, the spread of the prices or the severities, the number of distractors, whether a stale or conflicting item is present), never the oracle, the grading code, the hidden-file shapes or the seed semantics. Level 1 reproduces the existing dev and validation splits byte for byte (the hashes of the committed files are pinned by a test). A sealed test split is never generated by this stage.
B3 Calibration (free part): the generator reports, for each level, the size of the task and the number of traps, and a test shows that each level's hidden answer is derivable from the fixture (the oracle's own solver passes every generated task).
B4 Calibration (paid part, stage S1, not in S0.7): a headroom screen for each model: b0 or GP on 14 tasks of each level; the level whose pass rate lies between 30% and 70% (3 to 11 of 14) is the working level for that model; no level in the band means no comparison for that model.
