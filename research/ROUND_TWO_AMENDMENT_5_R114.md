## 1. What round two found at commit `909880b7` (registered as R0097 to R0105)
Four defects of the measuring tools, each found by reading what the model was shown and answered, not by a score:
* **W09** (R0104): the oracle compares the order ids `order-1.txt` to `order-3.txt` with a ledger keyed by whatever the model sent (`order-1`: the goal names the orders without an extension), so `all_orders_placed_once` is false although every order was placed exactly once, and the in-flight kill never fires because the service compares the held order id with the exact string `order-2.txt`.
* **`parse_error`** (R0098): two d0 runs of TC-003 ended `parse_error` after a retry that returned about 2,760 tokens of unusable text; the raw reply is not kept, so the cause is unknown.
* **W12** (R0103): in all 14 runs the model was never offered `mcp__notes__write_note`: the default menu keeps the 10 best-scoring of the 56 tools for the goal and the list for the W12 goal has `mcp__notes__read_note` but not the write tool. 0 of 14 measures the menu, not the model.
* **TC-006 live** (R0105): the live world builds its tools as `_Tool(name)`, whose description is the name and whose argument schema is empty, so the model guessed `path` for `relative_path`; every read failed. 0 of 3 measures the harness.

## 2. What is changed (and only this), with the rule each change must meet BEFORE it is merged
1. **W09 order ids.** One function `canonical_order_id` (strips a trailing `.txt` and surrounding spaces) is used by the order service for the ledger key, the request log and the hold comparison, and by `assess_w09` for the expected orders and the final effects. *Tests that fail on the old code:* the observed effects of R0104 (`{"order-1": 1, "order-2": 1, "order-3": 1}` against orders `order-1.txt`...) give `all_orders_placed_once` true; a service given the order `order-2` while `hold.json` names `order-2.txt` holds the reply (`api_committed_holding` appears); the same with the ids swapped. *Tests that must keep passing (negative controls):* a duplicate effect (`order-2` twice) is still a hard failure; a missing order (`order-3` absent) still makes `all_orders_placed_once` false; the scripted W09 case passes unchanged.
2. **Raw reply of an unusable decision.** When `decide_next_action` ends in `parse_error`, the decision carries `raw_first` and `raw_retry` (each cut to 4,000 characters), and the loop keeps them in that step's `tool_result` under `parse_error`. *Tests:* a provider that answers non-JSON twice leaves both texts in the step; a normal decision is unchanged; a retry that is cut at the allowance twice (`LLMReplyCut`) leaves an empty `raw_retry` and the reason.
3. **W12 sees its tools.** `run_w12` forces `DELENTIA_TOOL_MENU=full` in the episode's environment. *Test:* with that environment the real ranking code is off (`ranked_enabled()` false) and the full menu contains `mcp__notes__write_note`; the same test fails without the setting (the ranked menu does not contain it), using the real tool list and the real goal, no model.
4. **TC-006 live world tools.** `DirWorld.list_tools` returns tools with the real description and argument schema of `delentia_read_repo_file`, `delentia_write_repo_file`, `delentia_crawl_url` and `delentia_recall`, taken from the runtime's own registry. *Tests:* each tool's schema names its required arguments (`relative_path`; `relative_path` and `content_text`; `url`; `query`); the menu text the model gets contains `relative_path`; the scripted TC-006 cases pass unchanged.
5. **A check that would have caught items 3 and 4 (so it does not happen a fifth time).** `research/live_menu_check.py`: for a live workflow it builds the real tool list and the real menu for its goal and reports (a) every tool the workflow needs is in the menu and (b) the menu text contains the argument names the workflow's calls use. It is run (and printed) by `paid_round_two.py preflight` for the stages that use it and refuses the stage when (a) or (b) fails. *Tests:* it fails for the W12 goal with the default menu and passes with the full menu; it fails for a tool with an empty schema and passes for the real one.

## 3. The ranker question (not code; the Architect decides after the measurement)
A tool of an external server can drop out of the ranked menu while its sibling stays (W12). Whether the ranker should keep the write tools of a server when its read tool is shown is a product decision. Written before any measurement: `research/tool_menu_external_goals_r114.json` holds at least 40 labelled goals over at least four synthetic external servers (notes, tickets, calendar, mail-like), each naming the tools the goal needs; candidate rule R1 = "when a read-type tool of an external server is in the ranked menu, add the write-type tools of that server". Measured offline with the real ranking code: recall of ALL needed tools, mean menu size, and the same on the existing built-in set (`tool_menu_goals_round56.json`). The rule is proposed for adoption only if, on the external set, recall rises by at least 10 percentage points, the mean menu grows by at most 2 tools, and on the built-in holdout recall falls by no more than 1 point; the report is given to the Architect, who decides. Nothing about the default menu changes in the code of items 1 to 5.
